// capabilities

Everything a university
backend needs

Built with production patterns — role-scoped permissions at object level, async task automation, Redis caching, and sandboxed code execution.

🎓
Semester Lifecycle Automation

Celery tasks fire at configured deadlines to transition semesters Inactive → Active → Completed, cascading status changes to allocations and enrollments automatically.

⚡
Dual-Mode GPA Engine

Absolute grading for small cohorts (<20 students). Automatically switches to z-score bell curve normalization using population standard deviation for larger classes.

🔐
Object-Level Permissions

JWT auth with Django Groups (Admin / Faculty / Student). Every write endpoint enforces has_object_permission — faculty can only modify their own allocations.

🚀
Two-Layer Redis Cache

Admin/faculty data warmed by Celery at semester activation (10-min TTL). Student enrollment cache built on first access with timeout=None — bypassed on search/filter params.

📋
Two-Party Result Confirmation

Faculty trigger result calculation via a UUID confirmation-token email flow. Admin approves; the Celery task then applies GPA, marks enrollments Completed, and stores the transcript.

☁️
Sandboxed Code Execution

Python, C/C++, and Java each run in their own Docker container with 2 replicas. Accepts single files, multi-file uploads, and .zip archives with auto-detected entry points.

Result confirmation flow

GPA calculation is a sensitive, irreversible operation. A two-party UUID token confirmation flow ensures no accidental trigger — faculty requests, admin confirms, faculty applies.

1
Faculty
Request result calculation
Hits GET /api/faculty/allocations/{id}/calculate-result/ — creates a ChangeRequest with a UUID token.
2
System (Celery)
Email sent to active admin
Celery sends confirmation email containing a signed link to /api/admin/change-request/confirm/{uuid}/
3
Admin
Confirms via token link
ChangeRequest status flips to confirmed. Only then can the faculty apply it.
4
Faculty
Applies the change
Patches status: applied — the system runs the GPA engine, marks enrollments Completed, and locks the allocation.
ChangeRequest states
pendingawaiting admin
confirmedready to apply
appliedGPA computed
declinedvalidation failed
expiredtoken expired
Guarded against: No enrollments, null obtained marks, or already-calculated results — any of these decline the request automatically and return 400.

// cache architecture

Two-layer Redis caching

Cache is populated proactively by Celery tasks — not reactively on first request. Writes always invalidate the affected key before triggering the cache task to rebuild.

Layer 1 — Admin & Faculty
Celery-warmed, write-invalidated
Populated at semester activation by cache_faculty_data_task and cache_student_data_task. Every write hits cache.delete(key) then re-enqueues the task.
admin:faculty_list
admin:faculty:department:{dept_id}
admin:faculty:designation:{key}
faculty:{username}:allocations
faculty:{username}:{allocation_id}:assessments
TTL: 10 min (admin)  ·  5 min (faculty)
Layer 2 — Student Enrollment
On-demand, never expires
Built on first access after login. Stores the student's available allocations with enrollment confirmation state. Set with timeout=None — persists until explicitly cleared on enrollment action.
enrollments:{class_id}:semester:allocations
enrollments:{student_id}:{class_id}:data
student:dashboard:{username}
faculty:dashboard:{username}
TTL: None (enrollment data)  ·  5 min (dashboards)
⚠ Cache bypass: Any request with search or ordering query parameters skips the cache entirely and hits the database directly — filter logic runs on the full queryset, not on the cached list.
